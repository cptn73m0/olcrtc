# Дефект: простой 55-56 секунд при ротации сессии

Дата: 2026-10-27
Статус: гипотеза, требуется воспроизведение

## Симптом

Клиент показывает "подключено", но трафик не идет. Telegram висит на
"Соединение", пока пользователь вручную не переподключит VPN. На сервере в это
время нет ни одной живой сессии: `Current peers count: 0`.

## Измерения на рабочем сервере

Сервер: Ubuntu 20.04, olcrtc-panel 0.3.0, инстанс 10 (`jitsi` + `datachannel`,
комната `meet.egovm.ru/denuwa-tunnel-101`).

Три подряд замера от закрытия сессии до следующего успешного открытия:

| Закрытие | Следующая сессия | Простой |
|---|---|---|
| 08:04:29 | 08:05:24 | 55 с |
| 08:06:01 | 08:06:57 | 56 с |
| 08:07:35 | 08:08:31 | 56 с |

Внутри каждого окна в журнале сервера:

```text
server: AcceptStream(control) error - reinstalling session: io: read/write on closed pipe
handshake: discarding stale stream (attempt 1): read hello: handshake: frame too large: 2065850724 > 65536
handshake: discarding stale stream (attempt 2): ...
handshake: discarding stale stream (attempt 3): ...
handshake failed: read hello: handshake: frame too large: 2065850724 > 65536
session closed: id=... reason=reconnect
```

Число `2065850724` одинаковое во всех попытках: читается один и тот же остаток
буфера, а не свежие данные.

Для сравнения, нормальная ротация в те же сутки занимает 3 секунды
(07:59:35 закрытие, 07:59:38 открытие) и проходит без ошибок handshake.

## Код

`internal/server/serve.go:131` - `acceptHandshake`.

```go
for retry := 0; retry <= maxStaleRetries; retry++ {
    stream, err := session.AcceptStream()
    ...
    hello, sessionID, err := handshake.Server(stream, s.authHook, s.localPeerID())
    if err != nil {
        _ = stream.Close()

            continue

        logger.Warnf("handshake failed: %v", err)
        tunnelcore.ResetPeer(s.ln)
        s.reinstallSession(ctx, session)
```

`internal/server/link.go:243` - `swapSession` при переустановке возвращает сервер
в состояние ожидания handshake:

```go
s.sessionID = ""
s.deviceID = ""
```

`internal/server/serve.go:78` - пока `sessionID` пуст, сервер обязан принять
handshake, и первым же стримом из accept-очереди считает управляющий.

## Гипотеза

У стримов smux нет типа, тип определяется только содержимым. После сброса
`sessionID` сервер ждет кадр `HELLO` на первом попавшемся стриме, но клиент об
этом сбросе не знает и продолжает открывать стримы под данные (новые
TCP-соединения пользователя). Первые 4 байта такого стрима - не длина кадра, а
полезная нагрузка, отсюда `frame too large`. Три попытки "выбросить устаревший
стрим" выбрасывают три стрима с данными, затем `ResetPeer` рвет транспорт,
клиент переподключается, и цикл повторяется.

Почему цикл занимает именно 55-56 секунд, пока не доказано. Кандидаты:
backoff переподключения на стороне клиента, время успокоения транспорта после
`ResetPeer`, либо серия повторных переустановок до удачного совпадения таймингов.
Измеряется на стенде.

## Что чинить

1. Разметить стримы: первые байты каждого стрима несут тип (`HELLO` или `DATA`).
   Тогда сервер в режиме handshake отбрасывает именно `DATA`, не трогая
   транспорт. Требует синхронного обновления обеих сторон и версии протокола.
2. Не переустанавливать сессию по единственной ошибке управляющего стрима.
   Пометить сессию как подозрительную и отдать решение liveness.
3. При смерти сессии рвать транспорт сразу, чтобы клиент пересоздавал WebRTC,
   а не долбился в мертвый канал.

Порядок: пункт 2 и 3 - малые правки, пункт 1 - смена формата.

## Как проверять

1. Стенд: локальный `cnc` -> Jitsi -> `srv` на VPS.
2. Принудительная ротация каждые 60 секунд, не менее 30 циклов.
3. Критерий: разрыв между закрытием и открытием меньше 5 секунд в 30 из 30
   циклов, в журнале нет `frame too large`.
4. Юнит-тест на `acceptHandshake`: первым в очередь кладется стрим с данными,
   ожидается, что он отброшен без `ResetPeer` и следующий принимается как
   handshake.

## Что не делать

- Не увеличивать `maxStaleRetries` и не прятать ошибку: это маскирует симптом.
- Не поднимать `liveness` ради обхода: таймауты уже подняты до 30 с, дефект
  от этого не меняется.
